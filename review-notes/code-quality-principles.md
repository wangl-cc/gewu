# 代码质量原则（用户确认，2026-11-24）

核心：重点是代码质量、可维护性、可审阅性。修完 bug 以后要问：实现本身是不是更容易理解、修改和审阅了？"修了几个 bug、测试都过了"回答不了这个问题。

## 1. 完整审阅，不抽样
沿模块和调用关系把整个实现看完，不要挑几段代码看。重点找单看一个函数发现不了的问题：跨函数的状态流动、重复的逻辑、边界不清。

## 2. 同时查过度工程和工程不足
- 过度工程：把简单的事拆得太复杂，抽象没有带来收益。
- 工程不足：平铺直叙、脚本式的代码，职责混在一起。
- 要问：抽象和职责划分合不合适？现在的做法符不符合该生态的最佳实践？

## 3. 讲清生命周期、状态和副作用
每一份状态都要能回答四个问题：归谁管？谁能改？什么时候失效？一次操作会连带触发什么？
例子（这一类要逐条核实，并把同样的判断用到整个代码库）：
- 绘制代码里同时改滚动位置、列宽，还触发查找高亮刷新 → 读渲染代码的人能看清一次渲染会改哪些持久状态吗？渲染路径不应该改持久状态。
- 源数据行号和排序后的视图行号都是裸整数 → 两个含义不同的值传反了，类型系统能发现吗？应该用不同的 newtype。
- 查询状态分散在多个字段里，列名、列宽等靠几个平行集合手动同步 → 代码是不是允许构造出业务上无效的组合？
- "最多一个查询在跑、只保留最新请求"写在 UI 层 → 这条规则能脱离窗口单独读懂、单独测试吗？

## 4. 用不变量，不到处写防御性代码（特别强调）
遇到罕见状态，先问它为什么会出现、应该在哪里保证正确，再判断各处的检查还有没有必要。要在源头建立不变量，而不是在每个使用点打补丁。

## 5. 新增的复杂度要讲得出理由
行数是追问设计成本的信号（"增删多少？""为什么又多了一百多行？"）。要说明增加了什么，又消除了哪些重复、耦合或理解成本。

## 6. 审阅结论要落实到改动里
交付时逐条对应前面指出的问题（架构、状态分散、副作用……）：改了什么，还有什么保留，保留的理由是什么。

## 7. 评审意见本身也要经得起评审
别人（包括另一个模型）给的清单不要直接排优先级照做。先对每一条作出技术判断：哪些是对的、哪些不对、理由是什么。已实现的打勾，有分歧的写理由。

## 8. 移植时判断什么值得保留
不必完全对照旧实现。要能解释哪些行为必须保留，哪些历史做法可以舍弃。

## 9. 大改前先留可比较的基线
大改之前先 commit 当前版本，让改动可以比较、容易审阅。不规定必须拆成几个提交。

## 通用（已有）
- 一致性：同类的事用同一种方式处理。不一致本身就是问题，不能当小事。
- 一个清晰的模型、明确的职责边界、没有残留概念、好的命名。
- 讨论时先查证事实（代码、文档、当前版本），拿不准的地方标明是推断。
